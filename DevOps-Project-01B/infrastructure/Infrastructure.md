# AWS Infrastructure for Java Application

   This directory contains Terraform configurations to set up the AWS infrastructure for the Java application deployment. The infrastructure is a highly available, Multi-AZ 3-Tier architecture, secure and scalable that follows follows AWS best practices.

## Architecture Overview

The infrastructure consists of:

   - A per-environment VPC with public, private-application, and private-database subnets across two Availability Zones
   - An internet-facing Application Load Balancer (ALB) in the public subnets, terminating TLS with an ACM certificate that is DNS-validated through Route 53
   - EC2 instances running the application in Docker, in the private application subnets, managed by an Auto Scaling Group (target-tracking on CPU utilization)
   - Amazon RDS for MySQL, Multi-AZ, in the private database subnets
   - Amazon ECR for the application's Docker images
   - No bastion host — administrative access to EC2 instances is via AWS Systems Manager - Session Manager only; there is no SSH access to any instance
   - CloudWatch monitoring/alarms, CloudTrail auditing, VPC Flow Logs, and SNS email alerting
   - A GitHub Actions OIDC IAM role for keyless CI/CD authentication to AWS

## Prerequisites

1. **AWS Account and Credentials**
   - AWS account with appropriate permissions
   - AWS CLI installed and configured
   - Access key and secret key with necessary permissions

2. **Tools**
   - Terraform >= 1.10.0 (required for the native S3 backend locking used here)
   - AWS CLI >= 2.0.0

## Usage

1. **Bootstrap remote state (once per environment)**
The main configuration's S3 backend needs a bucket to exist before it can be initialized, so state storage is bootstrapped as a separate, self-contained Terraform root:
```bash
   cd infrastructure/bootstrap
   terraform init
   terraform apply -var="environment=dev" -var="aws_region=us-east-1"
```
This creates a versioned, encrypted, fully private S3 bucket named <environment>-terraform-state-<account-id>.

State locking: this project uses Terraform's native S3 state locking (use_lockfile = true in version.tf, available in Terraform >= 1.10), so no DynamoDB lock table is required.

2. **Generate the backend config and initialize**
```bash
   cd infrastructure
   ./scripts/generate-backend-configs.sh dev
   terraform init -backend-config=envs/dev-backend.hcl
```

3. **Configure variables**
Each environment has its own tfvars file under envs/ — dev.tfvars, stage.tfvars, prod.tfvars. terraform.tfvars.example documents every variable; copy it as a starting point for a new environment:

Create a `terraform.tfvars` file:
```hcl
   aws_region         = "us-east-1"
   environment        = "dev"
   aws_region         = "us-east-1"
   vpc_cidr           = "10.0.0.0/16"
   public_subnets     = ["10.0.1.0/24", "10.0.2.0/24"]
   app_subnets        = ["10.0.11.0/24", "10.0.12.0/24"]
   db_subnets         = ["10.0.21.0/24", "10.0.22.0/24"]
   availability_zones = ["us-east-1a", "us-east-1b"]

   app_port             = 8080
   instance_type        = "t3.micro"
   asg_min_size         = 2
   asg_desired_capacity = 2
   asg_max_size         = 4

   db_name                    = "appdb"
   db_username                = "admin"
   db_instance_class          = "db.t3.micro"
   db_allocated_storage       = 20
   db_max_allocated_storage   = 50
   db_backup_retention_period = 1
   db_backup_window           = "03:00-04:00"
   db_maintenance_window      = "Sun:04:00-Sun:05:00"

   app_health_check_path = "/"

   db_engine_version      = "8.4"
   db_deletion_protection = false
   db_skip_final_snapshot = true

   domain_name = "your_domain_name.com"  

   alert_email = "youaddressegmail.com"

   github_repository = "Kenf-Azapmo/DevOps-Projects"
   github_branch     = "master"
```
stage uses 10.1.0.0/16 and prod uses 10.2.0.0/16, following the same subnet pattern — see envs/stage.tfvars and envs/prod.tfvars.

4. **Plan and Apply the Infrastructure**

```bash
   terraform plan  -var-file=envs/dev.tfvars -out=tfplan
   terraform apply tfplan  
```

## Module Outputs

outputs.tf exposes the following values for use by the CI/CD pipeline and for integration with other tooling:

1. **Networking**
   - vpc_id, vpc_cidr, availability_zones
   - public_subnet_ids, private_subnet_ids (application tier), db_subnet_ids
   - nat_gateway_ids

2. **Security**
   -  alb_security_group_id, app_security_group_id, db_security_group_id

3. **Computer and Load Balancing** 
   - alb_dns_name, alb_arn, alb_target_group_arn
   - auto_scaling_group_name

4. **Container Registry**
   - ecr_repository_url

5. **Database** 
   - rds_endpoint, rds_address, rds_port, rds_database_name
   - rds_secret_arn — ARN of the Secrets Manager secret holding the RDS master credentials

6. **Observability**
   - cloudwatch_application_log_group, vpc_flow_logs_group
   - cloudtrail_name, cloudtrail_s3_bucket

7. **DNS**
   - route53_zone_id, route53_name_servers, application_domain

8. **CI/CD**
   - github_terraform_role_arn — the OIDC-assumable role ARN GitHub Actions uses to run Terraform / deploy

   Usage example (consuming these from a script or another Terraform root via terraform output):  
```bash
   terraform output -raw alb_dns_name
   terraform output -raw ecr_repository_url
   terraform output -raw rds_secret_arn
```


## Security Considerations

1. **Network Security**
   - Each tier of the 3-tier architecture has its own security group, scoped to the minimum required source and port
   - The database subnets have no route to the internet
   - All application servers run in private subnets; only the ALB is internet-facing
   - No SSH — access is exclusively via AWS Systems Manager Session Manager, no bastion host

2. **Database Security**
   -  RDS instance in a private subnet, not publicly accessible
   - Access restricted to the application security group on port 3306 only
   - Master credentials managed and rotated by RDS via Secrets Manager (manage_master_user_password), never hardcoded
   - Automated backups enabled, storage encrypted at rest

3. **Access Management**
   - IAM instance role for EC2 (no static credentials on the host)
   - GitHub Actions authenticates via OIDC federation (iam_github.tf) — no long-lived AWS keys stored as GitHub secrets
   - Security groups scoped to minimal required access
   - VPC Flow Logs enabled

Note: the current github_terraform IAM role has AdministratorAccess attached for simplicity during initial build-out. For a production environment, this should be narrowed to the specific set of actions Terraform needs for this project.

## Monitoring and Logging

   1. **CloudWatch Metrics:** ALB unhealthy host count, ALB 5xx rate, RDS CPU utilization, RDS free storage space, ASG CPU utilization; all alarms notify the <environment>-alerts SNS topic.
   2. **CloudWatch Logs:** application logs, system logs, Docker container logs, VPC Flow Logs.
   3. **CloudTrail:**  multi-region trail with log file validation, stored in a dedicated, encrypted, versioned S3 bucket with lifecycle transitions to Standard-IA (30 days) and Glacier (90 days).

## Cost Optimization

   1. **Resource Sizing** right-sized instance types per environment (t3.micro for dev/stage, t3.small for prod)
   2. **Auto Scaling** capacity tracks demand via a CPU target-tracking policy
   3. **Storage Management** CloudWatch log retention capped at 14 days; CloudTrail logs transition to cheaper storage classes over time; ECR lifecycle policy keeps only the most recent 20 images

## Maintenance

   1. **Backup Strategy** automated RDS backups, retention period configurable per environment, point-in-time recovery enabled
   2. **Updates and Patches** new application versions are rolled out via an ASG instance refresh (rolling, 50% minimum healthy) after a new image is pushed to ECR
